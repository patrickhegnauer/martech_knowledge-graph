# Wiring reference

This document lists every `<!-- WIRE: ... -->` attachment point in the UI shell, plus the final
component form field → ontology property mapping. It exists so the real logic can be wired into
the existing markup without restructuring any page.

## WIRE points

| Page | Element ID | Intended behavior | Reuses |
|---|---|---|---|
| components.html | `search-components` | Filter table rows by name/id as the user types | none (client-side UI only) |
| components.html | `filter-components` | Filter table rows by context status / `component_type` | `martech-ontology.ttl` `component_type`, `definition`/`caveats`/`context`/`owner` presence |
| component-edit.html | (readonly-block) | Refresh the read-only CJA block from the **real** CJA API (currently reads `server.py`'s `/api/components/<key>`, which sources from the local `.ttl` files, not a live CJA pull) | CJA Semantic Layer MCP |
| data-files.html | (data files table) | List actual files on disk with real size/mtime | `graph_explorer.py` `load_graph()` auto-discovery of `*-instances.ttl` |
| data-files.html | `file-viewer` | Load a real excerpt (or full file) of the selected data file, read-only | `martech-ontology.ttl` / `*-instances.ttl` on disk |
| mcp.html | (tool table) | Expose `run_sparql` and `get_ontology_schema` over MCP | `run_sparql` pattern (conceptual, from `platform-mvp-handoff.md`), `martech-ontology.ttl` |
| mcp.html | `endpoint-placeholder` | Show live endpoint URL and deployment status once the MCP exists | future MCP server |

## Component form field → ontology property mapping

| Form field (`name=`) | Ontology property | Notes |
|---|---|---|
| `definition` | `martech:definition` | direct match (domain: Component) |
| `caveats` | `martech:caveats` | direct match (domain: Component) |
| `context` | `martech:context` | direct match (domain: Component) |
| `owner` | `martech:owner` | direct match (no fixed domain; reused across Requirement/KPI/Journey/Component/Feature) |
| `refs` (repeatable, with `refs_label`) | `martech:refs` | Component → `rdfs:Resource`; pointer to AEP's native graph, never duplicated |
| name (read-only) | `rdfs:label` | standard RDFS, not martech-prefixed |
| type (read-only) | `martech:component_type` | "metric" or "dimension" |
| **CJA component ID** (read-only) | **none** | no ontology counterpart — CJA-side identifier only, never persisted as a triple |
| **data view** (read-only) | **none** | no ontology counterpart — not present anywhere in `martech-ontology.ttl` |
| **CJA description** (read-only) | **none** | no ontology counterpart — distinct from the curated `martech:definition`; shown for reference only, never written to the graph |

The three flagged read-only fields are intentionally excluded from the ontology: the platform curates
business meaning (`definition`, `caveats`, `context`, `owner`) here, while raw CJA/AEP metadata stays
authoritative in AEP and is referenced only by pointer (`martech:refs`), never duplicated.

## graph.html — now live (no longer a WIRE point)

Unlike every other page, graph.html renders real data and is no longer a static placeholder:

- Data is generated by running `graph_explorer.py`'s `extract_full_graph()` against `martech-ontology.ttl`
  + `ecommerce-funnel-instances.ttl` + `login-journey-instances.ttl` (25 nodes, 27 edges, 238 triples
  total in the underlying graph), then embedded as a `const DATA = {...}` JS literal directly in the page.
- Rendering uses `vis-network`, vendored locally at `ui/vendor/vis-network.min.js` (copied from
  `node_modules/vis-network/standalone/umd/vis-network.min.js` after `npm install vis-network` in the
  repo root) — no CDN, matching the README's existing no-CDN convention.
- `#class-filters` checkboxes toggle node visibility by `group` (hiding a node hides its edges too).
- `#select-journey` walks `has_stage` → `measured_entity`/`measured_component` client-side over the
  embedded edge list (the same walk `graph_explorer.py`'s `extract_explorer_data()` does server-side)
  and dims everything outside the selected journey.
- `#node-detail-panel` is populated on node click from each node's `properties` payload.

**Regenerating the embedded data:** if the `.ttl` files change, re-run and re-paste the JSON:
```
python -c "import json, graph_explorer as ge; g = ge.load_graph(); print(json.dumps(ge.extract_full_graph(g)))"
```
then replace the `const DATA = {...};` literal in `ui/graph.html`. This is a manual step (no build
step / no server) — every other page stays fully static and JS-free; graph.html is the one exception,
by explicit request, since a network viewer isn't renderable without JS.

## query.html — now live (no longer a WIRE point)

query.html runs a real SPARQL 1.1 engine client-side and is no longer a static example table:

- Engine: [Oxigraph](https://github.com/oxigraph/oxigraph) compiled to WASM, installed via
  `npm install oxigraph` in the repo root, then vendored (no CDN):
  - `ui/vendor/oxigraph.web.js` — the package's `web.js` browser bindings, with every `export`
    keyword stripped (turned into a classic script instead of an ES module, since `type="module"`
    scripts are blocked by CORS when a page is opened via `file://`) and the unused async
    `__wbg_init` path removed (it referenced `import.meta.url`, a syntax error outside a module,
    and used `fetch()`, which doesn't work against `file://` either). What remains is exposed as
    `window.Oxigraph` (`Store`, `initSync`, term constructors).
  - `ui/vendor/oxigraph.wasm.b64.js` — the compiled `web_bg.wasm` binary, base64-encoded into a
    `const OXIGRAPH_WASM_B64 = "…"` string, so it can be decoded and passed straight to
    `Oxigraph.initSync()` as bytes — no `fetch()`, so it works from a local file.
  - `ui/vendor/graph-data.ttl.js` — the full text of `martech-ontology.ttl` +
    `ecommerce-funnel-instances.ttl` + `login-journey-instances.ttl`, embedded as JS string
    constants (`ONTOLOGY_TTL`, `ECOMMERCE_TTL`, `LOGIN_TTL`) for the same file:// reason.
- On page load, an inline script decodes the base64 wasm, calls `Oxigraph.initSync()`, creates a
  `Store`, and loads all three turtle strings into it (238 triples — verified to match
  `graph_explorer.py load_graph()`'s triple count exactly).
- `#select-sample-query` swaps `#textarea-sparql`'s content between the three sample queries, copied
  verbatim from `graph_explorer.py` (`run_sample_query()`'s funnel walk, `print_component_context()`'s
  component-context query — the default on page load — and `extract_explorer_data()`'s journey walk).
- `#btn-run-query` runs `store.query(textarea.value)` — genuinely arbitrary SPARQL, not limited to the
  three samples — and renders a results table built from the query's `SELECT` variables; parse/exec
  errors are caught and shown inline instead of throwing.

**Regenerating the embedded turtle:** if the `.ttl` files change, regenerate `graph-data.ttl.js`:
```
node -e "const fs=require('fs'); for (const [v,p] of Object.entries({ONTOLOGY_TTL:'martech-ontology.ttl',ECOMMERCE_TTL:'ecommerce-funnel-instances.ttl',LOGIN_TTL:'login-journey-instances.ttl'})) console.log('const '+v+' = '+JSON.stringify(fs.readFileSync(p,'utf-8'))+';');" > ui/vendor/graph-data.ttl.js
```
No other vendor file needs to change unless the Oxigraph version is upgraded (in which case
`oxigraph.web.js` needs the same `export`-stripping treatment, and `oxigraph.wasm.b64.js` needs
regenerating from the new `web_bg.wasm`). Like graph.html, query.html is a deliberate JS exception
to the otherwise fully static, JS-free UI shell.

## components.html — "Sync from CJA" is now a live simulated flow (no longer a WIRE point)

`btn-sync-cja` no longer has a `<!-- WIRE -->` comment of its own; it now opens a real config/connect/sync
modal (`#modal-cja-config`):

- **Config step** (`#cja-step-config`): a form for `client_id`, `client_secret`, `org_id`, and scope
  checkboxes (`cja:components.read`, `cja:dataviews.read`, `cja:segments.read`). "Save & Connect"
  validates all fields are present, then saves them to `localStorage` under `martechKG.cjaConfig` and
  advances to the data view step. A banner in the modal is explicit that this is simulated (still no
  real OAuth) and nothing here is ever transmitted — this part is unchanged by the persistence work below.
- **Data view step** (`#cja-step-dataview`): shown immediately (skipping the config form) on every
  subsequent open once a config exists — `#btn-cja-reconfigure` goes back to the config step,
  `#btn-cja-disconnect` clears the stored config. `#cja-dataview-select` offers three mock data views
  (`Production - Website`, `Production - Mobile App`, `Staging - Website`).
- **Sync** (`#btn-cja-sync`): as of the persistence layer (see the `server.py` section below), this now
  POSTs `{data_view_id}` to `POST /api/cja/sync` — a **real** network call, not a DOM-only simulation.
  The server looks up the same mock pull table (now server-side, `CJA_MOCK_PULL` in `server.py`) and, if
  the component doesn't already exist, writes it to `components-instances.ttl` on disk and returns the
  refreshed component list, which re-renders `#table-components`. If the local API isn't running, the
  fetch fails and the result area explains that `python server.py` needs to be started — it no longer
  silently falls back to a DOM-only fake sync.
- The toolbar's `#cja-connection-status` reflects connected/disconnected state on every page load and
  after every connect/disconnect. `#live-mode-note` separately reports whether the component **table**
  loaded from the local API (`GET /api/state`) or fell back to the five static example rows.
- **Context coverage** (`#context-coverage-value`): a counter above the toolbar showing what fraction of
  rows in `#table-components` carry the `badge-has-context` class, e.g. "60% (3 of 5)". Computed by
  `updateContextCoverage()` on page load and again after every sync, so pulling in a new, not-yet-curated
  component visibly drops the percentage — same idea as `index.html`'s static "Context coverage" counter,
  but live and recalculated from the actual table instead of a hardcoded number. Once component context
  editing (`component-edit.html`'s Save) is wired to a real store, this same function should be called
  after every save too, not just after sync.

Verified end-to-end (DOM + `localStorage` shim in Node): open with no config → config form shown;
missing-field validation blocks connect; valid connect persists config, flips toolbar status, and shows
the data view step; syncing a data view once adds exactly one new row; syncing the same data view again
reports "already up to date" instead of duplicating the row; disconnect clears `localStorage` and reverts
the toolbar status.

**Wiring this to the real CJA Semantic Layer MCP later** means replacing two things: the "Save & Connect"
handler (currently just validates + stores locally) with a real OAuth/token exchange against the MCP, and
the `CJA_MOCK_PULL` lookup in "Sync" with an actual components-for-data-view call. The modal's shape
(config step → data view step → sync) and every element ID stay the same, so only those two handlers need
to change — this is why the `<!-- WIRE -->` comments on the config form and the data-view step were kept
even though the surrounding modal is already live.

## ontology.html — new page, fully static

Added as an onboarding/reference page (nav position: right after Home) for anyone landing on the repo
cold — the intro, core-chain walkthrough, and class/property tables are copied verbatim from
`martech-ontology.ttl`'s own `rdfs:comment`s and `README.md`'s framing. No JS, no WIRE points: it's pure
static content and stays that way. `query.html`'s ontology sidebar and `data-files.html`'s raw excerpt
were deliberately left as-is rather than consolidated — they serve as quick in-the-moment reference while
those pages, unlike this one, aren't meant to be an onboarding page.

## server.py — the persistence layer (new)

The biggest gap after everything above was that nothing actually wrote back to the `.ttl` files —
`component-edit.html`'s Save was inert, CJA sync only mutated the DOM, journey generation only showed a
static example, and `graph.html`/`query.html` both ran off a snapshot hand-embedded at authoring time.
`server.py` closes that: a small local Flask app (`pip install flask`, `python server.py`, listens on
`http://localhost:5055`) that serves **only** a JSON API under `/api/*` — no HTML — with permissive CORS
so pages opened directly via `file://` can `fetch()` it. It reads and writes the same flat `.ttl` files
directly via `rdflib`, reusing `graph_explorer.py`'s and `journey_builder.py`'s existing functions rather
than duplicating their logic (`ge.load_graph()`, `ge.extract_full_graph()`, `jb.build_journey_from_csv()`
are called directly, unmodified).

**Every page that now calls this API degrades gracefully if it isn't running** — this was the explicit
design goal, verified for each page below: each `fetch()` has a `.catch()` that falls back to that page's
original static/embedded content, so `ui/index.html` opened via `file://` with no server running still
works exactly as it did before this change. A `#live-mode-note` (or `#engine-status` on query.html)
element on every wired page reports which mode is active.

| Endpoint | Method | Used by |
|---|---|---|
| `/api/state` | GET | `index.html` counters, `components.html` table, `journeys.html` table |
| `/api/components/<key>` | GET | `component-edit.html` (populates the form on load, via `?id=<key>`) |
| `/api/components/<key>/context` | POST | `component-edit.html`'s Save button |
| `/api/cja/sync` | POST | `components.html`'s Sync button |
| `/api/journeys/generate` | POST | `journeys.html`'s Generate turtle button |
| `/api/graph-data` | GET | `graph.html` (replaces the embedded `EMBEDDED_DATA` snapshot when live) |
| `/api/ttl-bundle` | GET | `query.html` (replaces the embedded `ONTOLOGY_TTL`/`ECOMMERCE_TTL`/`LOGIN_TTL` when live) |

**Component identification:** the UI's `component_key` (e.g. `product_views`) maps to the subject local
name `component_<key>` (e.g. `component_product_views`) — exactly how the existing example files already
name things. `find_component_file()` scans every `*-instances.ttl` for a matching `martech:Component`
subject to find which file to edit.

**Where CJA-synced components live:** the first sync creates `components-instances.ttl` — a home for
components that exist but aren't bound to any journey yet, distinct from the per-journey instance files.
This is intentionally forward-compatible with a future "bind an existing component to a journey stage"
feature (still an open gap — journey CSVs still expect a component's full definition inline per stage
row rather than referencing an already-curated component by key).

**Accepted trade-off:** `rdflib`'s Turtle serializer reformats whatever file it rewrites — hand
formatting/comments in an edited instance file won't survive its first save through this API.
`martech-ontology.ttl` itself is never written to, only instance files.

**Verification performed this session:** every endpoint was exercised against the real running server
(not mocked) — `/api/state`, a full sync → verify-on-disk → idempotent-resync cycle, a full
load → edit → save → verify-turtle-preview cycle on a real component, a full CSV → generate →
verify-file-on-disk cycle, and confirmed `graph.html`/`query.html` both pick up newly-written files
automatically (no manual re-embedding step needed anymore, unlike the "Regenerating the embedded data"
steps described earlier in this document — those are now only relevant as the fallback path). Every
page's fallback behavior (server not running) was also verified separately.

## Packaging: pip install + `martech-knowledge-graph serve` (repo restructure)

The whole repo moved from "clone and run scripts / open HTML files" to an installable package
(`pip install -e .` or `pip install git+<repo-url>`, then `martech-knowledge-graph serve`). This changed
how the pieces above are wired together, though none of the endpoint contracts or page behaviors changed:

- **`server.py` is now a factory** (`create_app(data_dir)`) instead of a module-level `app`, so the CLI
  (`cli.py`) can bind it to a caller-chosen data directory. Every place that used to glob
  `SCRIPT_DIR / "*-instances.ttl"` now globs the passed-in `data_dir` instead. The ontology stays pinned
  to the bundled `ontology/martech-ontology.ttl` inside the installed package — it's never read from or
  written to a user's data directory, consistent with the "no ontology changes" decision from the
  original handoff doc.
- **The server now serves the UI itself**: `Flask(__name__, static_folder=<bundled ui/>, static_url_path="")`
  plus an explicit `/` route for `index.html`. Confirmed `/api/*` routes are not shadowed by the static
  catch-all (Werkzeug prioritizes the exact route). This means `ui/*.html` pages are normally reached via
  `http://127.0.0.1:5055/...`, not opened directly — though every page still works opened as a bare file
  too (e.g. someone only copied the `ui/` folder), falling back exactly as before.
- **CORS is gone.** Since the UI and API are now same-origin, the `Access-Control-Allow-Origin: *`
  `after_request` hook was removed entirely — it's no longer needed.
- **Every page dropped its `const API_BASE = "http://localhost:5055"`** and switched to relative
  `fetch("/api/...")` calls. This is a pure simplification with no behavior change: a relative fetch from
  a page opened via `file://` still fails to resolve to anything real and falls into the same `.catch()`
  fallback path as before — verified by re-running the fallback tests after this change.
- **New**: `POST /api/demo/load` and an "Load demo data" button on `index.html` (`#btn-load-demo`,
  `#demo-load-status`). Copies `examples/*.ttl` from the package into the active data directory, skipping
  files that already exist — same idempotent-report pattern as `/api/cja/sync`. This is the only way to
  get demo content; `martech-knowledge-graph serve` always starts with an empty data directory, by design
  (a fresh install is meant to start empty, not pre-loaded).
- **`graph_explorer.py`'s standalone CLI mode** (`python -m martech_knowledge_graph.graph_explorer`,
  independent of the web UI) had its own path bug fixed as part of this move: it used to write
  `graph.png`/`explorer.html`/etc. next to itself, which becomes a read-only `site-packages` directory
  once pip-installed. It now writes to the current working directory, and its `load_graph()` default
  `script_dir` points at the bundled `examples/` folder (previously its own directory) so running it
  standalone still produces something useful out of the box.

Verified end-to-end after the restructure (not just individually): `pip install -e .` from a clean
checkout, `martech-knowledge-graph serve` from a different working directory, confirmed `/`,
`/components.html`, `css/`, and `vendor/` all resolve; confirmed a fresh data directory starts at
0 components / 0 journeys with no error (113 triples — the ontology schema alone); confirmed
"Load demo data" populates it, is idempotent, and both `index.html`'s counters and `components.html`'s
live table reflect it immediately; confirmed the `file://` fallback path still works with the new
relative-URL code, using a broken-fetch stub against the real page markup.
